# PDF_Rename_Expert — бачення розвитку

Документ фіксує узгоджене розуміння процесу, поточний стан, прогалини та план розвитку.
Статус: **чернетка для узгодження** (станом на версію 1.5.0). Позначки: ✅ зроблено, ➕ потрібно зробити, ❓ відкрите питання.

---

## 1. Процес, який автоматизує програма

1. У полі виконують роботу: заміна лічильника, технічна перевірка, монтаж АСКОЕ тощо.
2. Результат — **Акт технічної перевірки**. У ньому зібрано всю інформацію, яку треба внести в базу.
3. У цеху акт скануюють. PDF потрапляє в `Scan\Населення` або `Scan\Промислові`; 4-значний номер скану стає початком імені файлу.
4. Оператор у програмі за один прохід:
   - **перейменовує скан** за шаблоном (є, працює);
   - **вносить дані акту в базу** (поки що не реалізовано як єдина дія — див. розділ 5).

### Категорії абонентів

| Категорія | Особливості | Куди вносимо |
|---|---|---|
| **Населення** | Як правило 1Ф, пряме підключення. Без ТТ/ТН, зазвичай без коефіцієнта обліку. Ключ запису — EIC. Таблиця плоска: абонент = рядок | База Населення ❓ (структура ще не визначена) |
| **Промислові — сторонні** | Сторонні споживачі, підключені до наших підстанцій. Мають EIC. Структура «підстанція → приєднання», лічильник + ТТ + ТН + коефіцієнт | `Лічильники по підстанціям 2026.xlsm`, аркуш «база» |
| **Промислові — підстанції (технічний облік)** | Наші власні точки обліку на підстанціях. **Не мають EIC.** В базі сусіднього підрозділу позначені «Технічний» у стовпці B | `Лічильники по підстанціям 2026.xlsm` ❓ (спосіб позначення не визначений) |

## 3. Поточний стан (v1.5.0)

✅ Перейменування сканів за шаблоном, пошук споживача за EIC, режим «Технічний облік», АСКОЕ, експорт звіту, прев'ю PDF, довідка F1.

✅ **Вікно «Лічильники по підстанціям»** — універсальний редактор книги `.xlsm` (аналог VBA-форми `frmBase`):
- поля будуються за шапкою аркуша «база» (60 стовпців A..BH), групуються, дати й фази виводяться блоками;
- фільтр за підстанцією, пошук, пошук за останніми 5+ символами EIC / № лічильника, навігація;
- збереження, додавання, видалення рядка; списки з «Довідники»;
- журнал змін в аркуші «Історія_Змін»; друк картки / підстанції у PDF.

Технічно: читання через openpyxl (без Excel), запис через Excel COM (зберігає макроси, об'єднані комірки, форматування). Модулі: `meters_model.py` (логіка), `meters_excel.py` (читання/запис), `meters_form.py` (вікно).

### Головна прогалина

Вікно «Лічильники» — **ручний редактор**: оператор сам шукає запис і правит поля. Реальний процес інший: оператор має працювати **за актом**, а дані, які він і так вводить для імені файлу, повинні **автоматично йти в базу**. Зараз ці два світи (перейменування й база) не пов'язані.

## 4. Схема відповідності: поле акту → стовпець бази (Промислові)

Бланка акту в проєкті немає; схема побудована за шапкою `.xlsm` і полями програми. **Потребує звірки з бланком.**

| Блок | Поле | Стовпець | Статус |
|---|---|---|---|
| Ідентифікація | EIC-код точки | B | ✅ (для техобліку порожньо ❓) |
| | Підстанція | C (об'єднана) | ➕ |
| | Приєднання | E | ➕ |
| | Стан (працює / зруйновано) | D | ➕ |
| | № п/п | A | авто |
| Лічильник | Тип | F | ➕ |
| | № лічильника | G | ✅ |
| | Клас точності | H | ➕ |
| | Uн, Iн | I, J | ➕ |
| | Рік випуску | K | ➕ |
| | Схема підключення | L | ➕ (не те саме, що «Фаза» в імені ❓) |
| | Держповірка (кв./рік) | M, N | ➕ |
| | Наступна держповірка | O, P | ➕ (можливо, авто ❓) |
| | Клемна колодка | Q | ➕ |
| | Присутність АК ХОЕ | U | ➕ |
| АСКОЕ | Тип підключення | R | ➕ |
| | № модему | S | ✅ |
| | IP-адреса | T | ✅ |
| ТТ | Тип | V | ➕ |
| | № фаз A / B / C | W, X, Y | ➕ |
| | Номінали, коеф. трансформації | Z, AA | ➕ (коеф. можна рахувати ❓) |
| | Клас, Uном, рік | AB, AC, AD | ➕ |
| | Держповірка / наступна | AE–AF / AG–AH | ➕ |
| | Дата заміни (д/м/р) | AI, AJ, AK | ➕ |
| | Балансова належність | AL | ➕ |
| ТН | Тип, №, номінал U, коеф., клас, рік, Uном | AM–AS, BA | ➕ |
| | Держповірка / наступна | AT–AU / AV–AW | ➕ |
| | Дата заміни (д/м/р) | AX, AY, AZ | ➕ |
| | Балансова належність | BB | ➕ |
| Підсумок | Коефіцієнт обліку | BC | ➕ (ймовірно коеф. ТТ × коеф. ТН ❓) |
| Акт | Код виконавця | BD | ➕ |
| | Номер акту | BE | ➕ |
| | Дата акту (д/м/р) | BF, BG, BH | ✅ (дата вже є у формі) |

**Вводиться для імені файлу, але в нашу базу не йде:** назва й адреса споживача, вид роботи, вид перевірки, «Інвест», суфікс-належність ❓ (чи потрібно їх фіксувати в базі).

**Наразі збігається** з існуючими полями програми: EIC, № лічильника, дата акту, модем, IP. Решта (~45 стовпців із 60) — нові поля.

Для **Населення** набір значно коротший: лічильник, держповірка, АСКОЕ, акт; блоки ТТ/ТН не потрібні.

## 5. Цільова модель роботи

Один екран, одна дія: **«Перейменувати й занести в базу»**.

1. Оператор обирає скан і джерело (Населення / Промислові).
2. Вводить EIC (або позначає технічний облік) — програма знаходить споживача й **запис у нашій базі**; якщо запису ще немає — пропонує створити.
3. Поле акту, що вже є в імені файлу (дата, № лічильника, модем, IP, вид роботи), **вводиться один раз** і йде в обидва місця.
4. Додаткові поля (ТТ, ТН, поверки, АСКОЕ) — у згорнутих блоках під формою, лише для категорій, де вони застосовні.
5. Попередній перегляд: нове ім'я файлу **і** перелік змін у базі (було → стане).
6. Підтвердження → перейменування скану + запис у базу + запис у журнал змін. Якщо одна з частин не вдалась — оператор бачить чітке повідомлення, і стан не лишається «напівзробленим».

Ручне вікно «Лічильники по підстанціям» **лишається** як режим «виправити запис».

### Принципи

- **Їхня база — лише для читання.** Не відкривати на запис, не блокувати. Розбіжності між нею й нашою базою показувати, а не перезаписувати мовчки.
- **Наша база — одне джерело правди** для технічних даних. Усі зміни проходять через журнал.
- **Структуру не зашивати.** Поля — за шапкою; жорстко прив'язані лише ключові (EIC, підстанція, приєднання, № лічильника).
- **Не втрачати дані.** Перед записом — перевірка блокування файлу; заміна лічильника не стирає історію (❓ спосіб).
- **Одна дія для оператора.** Менше кроків — менше помилок.

## 6. Цільова структура даних

### Проблема поточної структури

Аркуш «база» — **одна широка таблиця на 60 стовпців**, де в одному рядку змішано різні сутності:

| Сутність | Стовпці | Як змінюється |
|---|---|---|
| Точка обліку (підстанція, приєднання, EIC) | B–E | майже ніколи |
| Лічильник | F–U | при заміні |
| ТТ | V–AL | при заміні |
| ТН | AM–BB | при заміні |
| Акт (останній) | BD–BH | при кожній перевірці |

Наслідки: заміна лічильника стирає старий (історія лише в журналі змін); немає зв'язку «цей скан → ця зміна в базі»; для Населення довелося б робити окрему таблицю з тими самими полями, і структури почали б розходитись.

### Рішення

Широку таблицю **лишаємо** (до неї звикли люди й VBA-форма), але під неї додаємо **журнал актів**:

```
                    ┌─────────────────────┐
  скан PDF  ───────►│  «Акти» (журнал)    │  1 подія по акту = 1 рядок, нічого не стирається
  (ім'я файлу)      │  № акту, дата,      │
                    │  виконавець, скан,  │
                    │  вид роботи, ...    │
                    └─────────┬───────────┘
                              │ оновлює
              ┌───────────────┴───────────────┐
              ▼                               ▼
   «база» (Промислові)             база Населення
   поточний стан точки             поточний стан абонента
```

- «база» і база Населення — **поточний стан**; читається швидко, як зараз.
- «Акти» — **історія подій**: з будь-якого запису видно всі акти, зі скану видно, що він змінив.
- «Історія_Змін» лишається дрібнішим журналом (зміни окремих полів); «Акти» — журнал подій.
- Стовпці BD–BH (код, № і дата акту) логічно перенести в «Акти», а в базі лишити посилання на останній акт (крок 4).

### Спільні правила для обох категорій

1. **Однакові назви й формати полів** («№ лічильника», «Клас точності», «Держповірка») і спільні довідники: одна форма обслуговує обидві бази.
2. **Один явний ключ запису:** EIC, а для технічного обліку — «підстанція + приєднання». Не «знайти за збігом тексту».
3. **Довідники в одному місці** (аркуш «Довідники»).
4. **Технічний облік — явна ознака**, а не «порожній EIC»: окремий стовпець «Тип точки» (сторонній / технічний / населення).

### Чого не робимо

- Не переходимо зараз на справжню БД (SQLite тощо): Excel — робочий інструмент, ним користуються інші, у ньому VBA-форма. Це окремий проєкт.
- Не розбиваємо «базу» на п'ять аркушів (лічильники, ТТ, ТН…): теоретично правильно, але ускладнює роботу в Excel.

### Порядок змін

1. ✅ Аркуш **«Акти»** і запис у нього (див. нижче).
2. ➕ Стовпець **«Тип точки»** (сторонній / технічний).
3. ➕ База Населення з тими самими назвами полів.
4. ➕ За потреби винести BD–BH з «бази» в «Акти».

### Журнал «Акти» (крок 1, реалізовано)

Аркуш створюється автоматично при першому записі. Один рядок — одна подія по акту.

| Стовпець | Зміст |
|---|---|
| Дата Час, Користувач | коли й хто |
| Подія | «Правка запису» або «Скан перейменовано» |
| Номер акту, Дата акту, Код виконавця | стовпці BE, BF–BH, BD запису |
| Підстанція, Приєднання, EIC, № лічильника | ідентифікація запису |
| Вид роботи, Вид перевірки | заповнюються при внесенні через перейменування скану |
| Скан (файл) | ім'я перейменованого PDF — зв'язок скану з базою |
| Рядок бази, Примітка | службове |

Поведінка зараз:
- у вікні «Лічильники» при **збереженні запису, де змінено дані акту** (номер, дата, виконавець; номер непорожній) додається рядок «Правка запису». Інші правки в «Акти» не потрапляють — вони лишаються лише в «Історія_Змін»;
- кнопка **«Журнал актів»** показує журнал (найновіші зверху);
- функція `register_act()` (`meters_excel.py`) готова для єдиної дії «Перейменувати й занести в базу»: вона дописуватиме подію «Скан перейменовано» з іменем файлу, видом роботи й видом перевірки.

## 7. Відкриті питання

Блокують проєктування екрана «Внести в базу»:

1. ❓ **Як позначати технічний облік у нашій `.xlsm`?** (слово «Технічний» у стовпці B, як у базі підрозділу, чи інакше). Визначає пошук і створення запису.
2. ❓ **Чи затверджена шапка й порядок стовпців `.xlsm`?** Від цього залежить, наскільки можна покладатися на літери стовпців.
3. ❓ **Де й у якій структурі база Населення?** Окремий файл чи аркуш, які стовпці, скільки записів (від цього залежить швидкість запису).
4. ❓ **Бланк акту** — потрібен зразок для остаточної звірки розділу 4.

Уточнення:

5. ❓ Чи всі стовпці A..BH заповнюються з акту, чи частина рахується (наступна поверка, коефіцієнти)?
6. ❓ Вид роботи й вид перевірки треба фіксувати в базі? У якому стовпці?
7. ❓ Заміна лічильника: перезаписуємо рядок чи зберігаємо історію старого?
8. ❓ Чи потрібна **періодична синхронізація** з базою підрозділу (нові EIC, зміни назв і адрес) і хто головний при конфлікті?
9. ❓ Чи кілька людей пишуть у базу одночасно (спільна папка)?

- Лише читання, без блокування їхнього файлу.

### Етап 5 — якість і підтримка
- Розбити `app_ui.py` (понад 1800 рядків, ~70 методів): винести довідку, гарячі клавіші, прев'ю PDF, фонові задачі (єдиний `run_in_thread` замість трьох `_poll_*_queue`).
- Прибрати глобальний змінний стан у `naming.py` (`WORK_CODES`, `CHECK_CODES`): повертати об'єкт правил.
- Матриця CI: додати Python 3.8 (збірка Win7), `ruff`, розділити dev- і build-залежності, закріпити версії.
- Автоматичні резервні копії `.xlsm` перед записом (наприклад, остання копія + дата).
- Захист від одночасного запису кількома користувачами (за потреби).

## 9. Ризики

| Ризик | Заходи |
