# Збірка й випуск (локально)

Домовленість: **збірки й випуски ведемо локально на ПК**. GitHub використовується як **резервне збереження** документації, структури й коду проєкту. Релізи на GitHub не створюємо, збірку через GitHub Actions не запускаємо.

## 1. Що де живе

| Що | Де |
|---|---|
| Код, тести, документація | репозиторій; копія на GitHub (`main`) |
| Збірка exe (`dist\`, `build\`) | лише локально, у `.gitignore` |
| Реальні дані (книги `.xlsm/.xlsx`, скани PDF, папка `124/`, `Scan/`) | лише локально, у `.gitignore` |
| Налаштування користувача, історія суфіксів | `%APPDATA%\PDF_Rename_Expert\` |

## 2. Звичайна збірка (Windows 10/11)

```powershell
pip install -r requirements.txt -r requirements-dev.txt
python -m pytest tests -q
pyinstaller --noconfirm PDF_Rename_Expert.spec
```

Результат: `dist\PDF_Rename_Expert.exe` (≈130 МБ; великі зайві пакети з глобального Python виключені в `.spec`). Якщо збірка падає з кодом 1 — exe, ймовірно, ще запущений: закрийте його. Файли `rules.json` і довідка F1 вшиті в exe (див. `PDF_Rename_Expert.spec`).

## 3. Збірка під Windows 7

Потрібен **Python 3.8.10 x64**. Запустіть `build_win7.bat`: він створює `.venv-win7`, ставить `requirements-win7.txt`, проганяє тести й збирає exe.

Окремо перевірте на Win7: наявність VC++ Redistributable та оновлень системи, роботу запису в Excel (`pywin32`) і друку PDF. На сучасному Python це перевірено лише тестами й ручним прогоном.

## 4. Версії

1. Змініть `version.py` (`__version__`), за потреби — довідку й `README.md`.
2. Додайте запис про зміни в коміт (формат: `feat:`, `fix:`, `docs:`, `chore:`).
3. Тег ставте **лише локально**, якщо потрібна мітка в історії: `git tag -a v1.5.0 -m "..."`. **Не пушите теги** на GitHub без потреби.
4. Правило нумерації: `1.МІНОР.ПАТЧ`. Нова функція — мінор (1.5 → 1.6), виправлення — патч (1.5.0 → 1.5.1).

## 5. Випуск користувачам

1. Зберіть exe (розділ 2 або 3), запустіть його вручну й пройдіть чекліст нижче.
2. Покладіть exe у спільну папку / передайте користувачам. Збірки зберігаються у `Releases\v1.x.y\` (папка в `.gitignore`, на GitHub не потрапляє): exe, довідка й `SHA256.txt`; старіші збірки — у `Releases\archive\`, щоб можна було відкотитись.
3. У тій самій теці залиште `INSTRUKTSIYA_KORYSTUVACHA_APP.md`.

### Чекліст перед випуском

- [ ] `pytest` зелений.
- [ ] exe запускається; головне вікно відкривається; F1 показує довідку.
- [ ] Перейменування тестового скану дає очікуване ім'я.
- [ ] «Лічильники по підстанціям»: відкриття книги, зміна й збереження поля, додавання й видалення рядка (**на копії книги**), друк картки в PDF.
- [ ] Аркуші «Історія_Змін» і «Акти» ведуться; макроси книги на місці (`Ctrl+Shift+F` в Excel відкриває VBA-форму).
- [ ] Книга, відкрита в Excel іншим користувачем, дає зрозуміле повідомлення про блокування, а не пошкодження.

## 6. Резервне збереження на GitHub

GitHub — це резерв **коду й документації**, не дані й не збірки.

- Зберігайте періодично (наприклад, в кінці робочого тижня й після суттєвих змін документації):
  ```powershell
  git status
  .\push_release.ps1      # тести + git push гілки main, без тегів
  ```
  або вручну: `git add -A`, `git commit -m "docs: ..."`, `git push origin main`.
- Перед комітом переконайтесь, що реальні дані не потрапляють у репозиторій: `git status` не має показувати `*.xlsm`, `*.xlsx`, `*.pdf`, `124/`, `Scan/` (вони в `.gitignore`).
- Тести на GitHub (workflow **CI**) запускаються автоматично при push — це допустима перевірка, вона не створює релізів.
- Workflow **GitHub Release** працює лише за ручним запуском і в звичайному процесі не використовується.

## 7. Резервні копії даних

Книги з даними (`Лічильники по підстанціям*.xlsm`, база Населення) **не потрапляють на GitHub** — для них потрібен окремий резерв:
- регулярна копія на мережевий диск / хмару за вашим регламентом;
- перед масовими змінами (наприклад, імпорт, зміна структури) — копія файлу з датою в імені.

У планах (див. [ROZVYTOK_PROEKTU.md](ROZVYTOK_PROEKTU.md), етап 5): автоматична копія `.xlsm` перед кожним записом із програми.
